# Checkpointed BrowserGym campaign

**WebArena isolation repaired (2026-09-28):** the runner replaces the pinned Reddit backend before every arm, checks its identity and persisted-state readback, and blocks scored calls without current isolation and evaluator qualification. The old `/init` path only configures the application; all historical WebArena comparisons without clean-start evidence remain invalid and their raw rewards are excluded from dashboard score views. MiniWoB is unaffected. Scores depend on the exact frozen controller and task cohort; see the [capability scorecard](capability-status.md#isolated-webarena-development-check) for current and preceding evidence.

Use this for a longer, auditable MiniWoB, WebArena-Verified, or original BrowserGym-core integration study. It runs one baseline/candidate pair per Docker invocation using the [BrowserGym study bridge](browsergym-study.md), then writes the independent reward report before scheduling another pair. No AgentLab, Python, browser service, database or dashboard package is installed on the host. The persistent dashboard is a read-only Node HTTP server bound to `127.0.0.1`; it serves derived summaries only, never keys or raw traces.

This document describes the maintained checkpointed runner, including its finite batch limits and at-most-three-retry implementation. Those are runner constraints, not universal campaign approval requirements. Apply the [Benchmark Improvement Loop](../../benchmark-improvement-loop/SKILL.md) authorization and evidence contract. Under sustained uncapped authorization, select operational batch limits without asking again; if this runner cannot express the experiment, use or implement a qualified alternative while retaining one cumulative ledger and task history. Do not create new directories to conceal exhausted attempts or task exposure.

## Start and monitor

Prepare a separate baseline skill directory. The campaign copies it into its private run directory so later cleanup or edits cannot change the baseline. Put the run directory under this skill's ignored `.runs/` directory or another private persistent location:

```sh
npm run gym:campaign -- \
  --run-dir /absolute/path/to/skill/.runs/miniwob-2026-09-27 \
  --baseline-dir /absolute/path/to/baseline/agent-browser-jev \
  --max-hours 8 --max-usd 10 --max-retries 3 --init-only

npm run gym:dashboard:service -- start \
  --campaign-root /absolute/path/to/skill/.runs --port 8765

npm run gym:campaign -- --run-dir /absolute/path/to/skill/.runs/miniwob-2026-09-27
```

To reserve a holdout, include it in `--cases` and also pass `--holdout-cases id,id` during initialization. Development cases run and converge first; each holdout then receives one attempt and cannot be unlocked by an ordinary retry note.

The service detaches from the invoking shell and continues until explicitly stopped. `status` checks both its exact PID and `/status.json`; `stop` terminates only that recorded PID. Its landing page aggregates campaign manifests plus pre-campaign `readiness.json` records beneath the campaign root. It promotes a real campaign over an older stale readiness record, but shows a genuinely newer readiness record while the next campaign awaits authorization. It refreshes every ten seconds and shows the current stage, iteration, frozen development first-attempt score, accumulated development score, current-candidate coverage, untouched-holdout score, task cohorts, spend, elapsed time, latest activity and measured impact of every change. Missing holdout data is shown as not reserved rather than silently merged into development results.

Experiment bundles with `readiness.json` can also carry `dashboard-evidence.json`; readiness checks alone are not their performance scoreboard. This optional schema1 index names relative report paths and exact SHA256 hashes, each report's `cohort`, `title`, `kind` (`public`, `authored`, or `components`), qualification, disposition, note and arm labels. The dashboard checks report hashes and containment before projecting allowlisted trial metrics. Public reports retain official reward separately from independent goal and scope reviews; authored and component outcomes do not become official reward. Positive denominators exclude expected negatives, while costs and work include them. Missing measurements remain unknown.

Optional hash-bound `reviews` point to audits with `trials` containing `report`, `sha256`, `id`, `arm`, `scope`, `independentGoal` and `falseCompletion`; include the review method and supporting evidence in the private audit. Only a review matching the exact raw report, case and arm can supplement that trial. A `negativeCheck` of `passed` or `failed` can correct an expected-negative audit; it cannot turn a positive into a negative. The projection and detail page retain its original raw negative flag alongside the reviewed verdict. Optional `accounting` points to a hash-bound record of campaign measured cost, cumulative conservative cost, remaining allowance, reconciliation and deadline; the index supplies `maxCostUsd`. Missing or changed sources are visibly excluded, with incomplete coverage reported. The homepage shows separate cohort comparisons, and each experiment page adds expandable trial details with source/report fingerprints. Completed experiment detail pages use manual refresh so automatic reload cannot collapse the trial rows being inspected; the homepage stays live. Older readiness bundles without this index remain explicitly summary-only. Raw reports, goals, pages, tokens and keys are never served.

`npm run gym:campaign -- --run-dir /path --status` gives one campaign's state as JSON. `--once` runs just the next pair; omitting it sweeps pending pairs until a limit, failure requiring a skill change, or completion. The default campaign covers 21 MiniWoB task IDs with seeds 11 and 12; override with `--cases id,id --seeds 1,2` only at initialization.

To run the separately labeled integration suite, add `--suite integration` when initializing. It defaults to three original BrowserGym-core tasks with seeds 11 and 12. The site, Python task classes, evaluator, browser and helper all stay inside the same short-lived Docker container; no extra host service or account is needed. The suite is useful for multi-page regression coverage, not a public benchmark score. The manifest freezes the suite choice; omit it when resuming.

For WebArena-Verified, first qualify reset isolation and run both evaluator controls in the [study workflow](browsergym-study.md), then initialize with `--suite webarena-verified --webarena-environment /absolute/path/to/environment.json`. The original default public development cohort is tasks `399`, `404`, `595`, and `650` with seed 0; explicit continuation campaigns may also use supported public tasks `596`, `600`, `603`, and `605`. All eight are now development evidence. A new campaign must select a different unopened task, add only its identifier to the supported adapter contract, include it in `--cases`, and name it in `--holdout-cases` without inspecting its intent. The runner withholds that task until development has no pending or retryable task and runs it only once. The manifest records both cohorts and the sanitized environment identity. This runner requires finite `--max-hours` and `--max-usd` values at initialization. Choose them within user limits, or as operational batch limits when the user has authorized uncapped work.

The private directory contains `manifest.json`, numbered hash-chained events, paired reports and exact skill source snapshots for every version tested. Trial events record task/seed, attempt, baseline/candidate reward verdict, failure class, source fingerprints, report hash, provider charge and scoped cleanup. A new candidate runtime fingerprint creates a change event with changed-file hashes and a required `--change-note` explaining the edit. Do not put secrets in that note. The hash chain detects accidental or unsanctioned edits when the runner resumes, but these local files are not tamper-proof. Reports may include synthetic page text and should stay private; the OpenRouter key is not recorded.

## Interpret scores by source version

The frozen first-attempt view includes only development trials on the initial candidate fingerprint. Holdouts run after feedback and are excluded. If candidate code changed before that initial sweep finished, remaining slots are untested for that frozen candidate, not silently folded into its score.

Accumulated development (`views.repairedDevelopment` in JSON for compatibility) shows each task's latest result and can combine source versions. Current candidate development (`views.currentDevelopment`) includes only results matching the most recent recorded candidate fingerprint; `currentDevelopment.untested` names the missing tasks. The dashboard keeps both visible. Terminal `complete` describes campaign scheduling, not full coverage of the final implementation. This is the latest recorded snapshot, not a claim about unrecorded working-tree edits.

An unfinished pair is counted under `incompleteComparisons` and excluded from paired scores; keep its partial actions and charges. `invalidComparisons` instead identifies evidence rejected for isolation or another scoring defect. An incomplete arm does not invalidate separately verified pairs. Starting another internal run directory does not reset task exposure, retry counts, any applicable user deadline or cumulative spending; retain a shared ledger and snapshot history across the campaign.

Before claiming a final improvement, run the relevant regression study of one frozen candidate within the existing authorization and report it alongside the development history. Preserve all old reports. The 1.3.0 dashboard can reinterpret their provenance without editing those historical records. Follow the [general change acceptance rules](study-gym.md#accept-a-general-improvement).

## Improvement loop and limits

The initial sweep does not rerun failures. Review a failed report and distinguish harness/infrastructure problems, unsupported widgets, missing exact values, and actual incorrect actions. If a general skill or benchmark-adapter change is justified, edit it, run the affected regressions, then resume with `--retry case/seed,case/seed --change-note "Reason for the change"`. Only the named tasks can retry under that change; unrelated failures are not blindly rerun. In this runner, a failed task can run once initially plus at most the configured retries (the CLI accepts zero through three). A retry is offered only after runtime or benchmark-adapter source files change; a documentation-only edit does not unlock one. Record a currently unsupported case without spending retries using `--defer case/seed --reason "Observed inaccessible slider"`. Do not treat a defer as a pass.

Repeat the failing seed to diagnose the fix, use unused seeds for variation checks, and reserve unopened task families for transfer evaluation. Preserve existing failure reports. Do not silently delete failures, reuse the same seed as evidence of generalization, or commit/publish skill changes without the user's separate request.

For a local component regression, write its report inside the private campaign directory, then use `--record-validation /absolute/path/to/report.json --reason "what it checked"`. The campaign verifies a measured component report, records its hash, pass count and charge in the event chain, and counts that charge toward the same spend cap. Recording is read-only with respect to the report; do not record a report twice.

After independently reviewing actions and persisted effects, attach a supplemental scope audit with `--record-scope-audit /absolute/path/inside/run/scope-audit.json`. The JSON uses `kind: "browsergym-scope-audit"`, a named `method`, and `entries` containing the recorded `reportSha256`, `arm`, `scope` (`passed`, `failed`, or `unassessed`), `goalVerified` (`true`, `false`, or `null`), and a concise `reason`. The command verifies report hashes and appends an audit event. It never rewrites official reward, source reports, charges or attempts. This review is evaluator-side work, not caller intervention during the episode. The dashboard separately displays full reward, completion reports, return reasons, caller assistance, reviewed goal completion, scope violations and unassessed fields. A scope audit cannot rehabilitate an invalid comparison.

The campaign stops before starting a pair if its configured duration has elapsed, if any trial's model charge is unmeasured, or when accumulated charges reach the configured cap less a 5% reserve (up to $0.50). A single already-running pair may still incur additional provider charges before its result is known; use a provider-side account cap for an absolute billing guarantee. The runner forwards its deadline signal to the Docker study for scoped cleanup. If Docker cleanup fails or the study is incomplete, the campaign stops for inspection. The dashboard and campaign can be restarted from their audit files. The dashboard service deliberately remains running across terminal exits; stop it explicitly with `npm run gym:dashboard:service -- stop --campaign-root /absolute/path/to/skill/.runs` when it is no longer wanted.

If any Docker trial has unknown model charges, inspect its report and cleanup first. This includes a completed reward report whose helper encountered a provider error; outcome scoring does not settle provider accounting. Once the container is gone, `--reconcile-run RUN_ID --reason "why the trial failed"` reads the configured key's cumulative usage from OpenRouter and reserves that entire amount against the campaign budget. The audit retains the failed trial and the reconciliation event; the dashboard distinguishes measured charges from this conservative reserve. This does not convert the failed trial into a pass or restore its retry slot. Only then may an explicitly targeted infrastructure retry run. If the key-usage check fails or cleanup is uncertain, leave the campaign stopped.


Supplemental scope reviews can include a nonnegative integer `callerInterventions` when frozen runner and trace evidence establish a missing historical measurement. Recorded intervention counts take precedence. Scope remains `unassessed` when only task reward is independently checked; a correct MiniWoB outcome is not a certificate of arbitrary action scope. Status output drains before exit so large campaign JSON remains complete when piped. Explicit no-dispatch evidence permits zero charge for setup failures; missing post-dispatch usage stays unknown.

## Planning-assistance attribution

An experimental helper may return a separate `assistance` record with kind, model, intervention/call counts, token counts, elapsed time and provider cost. Reasoning-only guidance is assistance even when Jev executes every gesture. The study records it in actor telemetry, the campaign retains it in trial events and adds its cost to the campaign ceiling. Unknown assisted charges stop dispatch; missing intervention telemetry stays unknown. Scope audits and the dashboard distinguish verified assisted goals from autonomous goals. Preserve the original helper return and compare against equal-budget unassisted continuation before attributing a recovery to planning. This does not enable another model in the ordinary helper.
